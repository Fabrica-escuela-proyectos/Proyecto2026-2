## Trampas conocidas
- Spring Boot 4 movió autoconfiguraciones: Flyway necesita `spring-boot-flyway` y las migraciones van en `src/main/resources/db/migration/`; `@AutoConfigureMockMvc` está en `spring-boot-webmvc-test`.
- `Set.of(...)` (inmutable) sobre una entidad gestionada rompe `merge()`: usar `new HashSet<>(...)`.
- Hibernate valida el esquema (`ddl-auto: validate`); un cambio de entidad sin migración falla al arrancar.
- **Pruebas de integración:** extienden `AbstractIntegrationTest` (un PostgreSQL de Testcontainers por corrida; ya no usan `localhost:5432`). Docker Engine 29 exige **Testcontainers ≥ 1.21.4**; desde el 2026-10-10 el proyecto usa **2.0.5** (artefactos `testcontainers-postgresql` y `testcontainers-junit-jupiter`, clase `org.testcontainers.postgresql.PostgreSQLContainer`, sin genéricos) (con 1.21.3: "Could not find a valid Docker environment"; era la causa real del "problema de npipe" de Sprint 1). Usa `uniqueEmail()`/`uniquePhone()` y `createEnrolledAdmin()` (admin con MFA) del helper; la base y el contexto se comparten entre clases. Jackson 3: `tools.jackson.databind.ObjectMapper`, no `com.fasterxml`.
- **Auditoría y transacciones:** un servicio `@Transactional` que audita un rechazo y luego lanza la excepción **pierde el evento** por el rollback; declara esa excepción en `noRollbackFor` (ver `AuthServiceImpl.login`, `UserRegistrationService.register`).
- **Límites de intentos** (`security.rate-limit.*`): registro 5 por IP (el 6.º → 429), login/MFA 5 fallos → 429; el perfil `test` relaja el de registro. En memoria, una sola instancia. La IP sale de `X-Forwarded-For` (`server.forward-headers-strategy: native`).
- **Sin perfil por defecto (SEC-05):** `./mvnw spring-boot:run` usa `dev` por la propiedad `spring-boot.run.profiles` del pom; en IntelliJ o Docker hay que definir `SPRING_PROFILES_ACTIVE`. Sin perfil la app exige `JWT_SECRET` real y `DB_PASSWORD` (`ProductionSafetyGuard`) y no arranca con la clave `dev-only-…`. Render: `prod` (logs JSON).
- **Todo error lleva `traceId`** (= header `X-Request-Id`, filtro `RequestCorrelationFilter`); un cuerpo > 64 KB da 413 (`RequestSizeLimitFilter`); cabeceras CSP/Referrer/Permissions en `SecurityConfig` (la CSP estricta se omite en `/swagger-ui`).
- **`bookings` usa `EXCLUDE USING gist` (migración V10, extensión `btree_gist`):** anti-overbooking en la base por recurso. En Testcontainers y docker-compose funciona (usuario superusuario); **en Render hay que verificar que el usuario de la base pueda crear la extensión** (es "trusted" desde PG 13). `ddl-auto: validate` exige `INT` (no `SMALLINT`) para campos `int`.
- **Bloqueo de fila + Hibernate:** si una entidad ya se cargó antes en la misma transacción, `SELECT … FOR UPDATE` vía JPA devuelve la copia en memoria (estado viejo) aunque otra transacción haya confirmado un cambio. Para leer un valor bajo bloqueo usa consulta nativa (ver `ResourceRepository.lockAndReadActive`); un fallo así lo destapó la prueba de carrera de HU-16.
- **Horario efectivo (HU-21):** la disponibilidad y la creación de reservas usan `ResourceScheduleLookup.effectiveWindowsOn(ids, fecha)` (semanal menos cierres), no `windowsOn(día)`. Al reservar, con el recurso ya bloqueado se vuelve a llamar `isClosed(...)`.
- **Bloqueo compartido del servicio:** `BookingServiceImpl` llama `ServiceLookupService.lockForBooking` (`select active … for share`) ANTES de `findById`; desactivar/editar un servicio toma `FOR UPDATE`. En pruebas unitarias de reservas hay que simular `lockForBooking → true`.
- **Ayudantes de integración del Sprint 3** en `AbstractIntegrationTest`: `newProvider()` (negocio + servicio de 60 min + "Sala 1" asignada, L-V 08-20), `newResource`, `newClient`, `book`/`bookResult`, `upcomingMonday()`, `availableStarts()`. Ojo: un método `private` con la misma firma en una subclase no compila ("weaker access"); por eso no se llaman `nextMonday`/`freeSlots`.
- **Diagramas de componentes y paquetes se GENERAN del código** (`docs/arquitectura/diagramas/generar_diagrama_componentes.py` y `generar_diagrama_paquetes.py`, SVG + PNG con PyMuPDF): regenerarlos tras cambiar dependencias entre módulos; no editarlos a mano. El de despliegue es SVG a mano (PNG: `pymupdf.open(svg)[0].get_pixmap(matrix=pymupdf.Matrix(1.6,1.6))`).
- **Postman local:** `docker run -d --rm --name pg-newman -e POSTGRES_DB=reservas -e POSTGRES_USER=reservas_app -e POSTGRES_PASSWORD=<temporal> -p 25432:5432 postgres:16-alpine`, app con `DB_URL/DB_USERNAME/DB_PASSWORD/SERVER_PORT=28080 ./mvnw spring-boot:run`, y `npx --no-install newman run … --env-var baseUrl=http://localhost:28080`. Al terminar, el `mvnw` en segundo plano deja un `java` vivo en el puerto: cerrarlo por PID.
- JaCoCo acumula datos entre corridas: para medir cobertura usa `clean`. `.github/` debe estar en la **raíz** del repo para que GitHub lo lea (ya está ahí). El workflow `.github/workflows/build.yml` (tests → Sonar → build) usa `defaults.run.working-directory: reservas-backend` porque el `pom.xml` no está en la raíz; la config de Sonar vive en las propiedades del `pom.xml` y necesita el secret `SONAR_TOKEN`.
